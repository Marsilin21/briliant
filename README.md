# Бриллиант Монолит

Рабочая локальная версия существующего сайта с собственной админкой и серверной публикацией. Исходный дизайн и файлы логотипа сохранены. HTML/CSS/JS экспорта Tilda в корне остаются исходниками; сборка создаёт редактируемые шаблоны отдельно в `dist`.

## Запуск на Windows

Требуется Node.js 24 (проверено на 24.14.1). Запустите `start-monolit.ps1` либо:

```powershell
npm ci
npm run build
npm start
```

- Сайт: http://127.0.0.1:4180/
- Админка: http://127.0.0.1:4180/admin/
- При первом локальном запуске создаются пользователь `admin` и случайный пароль в `data/initial-admin.txt`. Этот файл веб-сервер не раздаёт.
- Пароль можно изменить в админке. `npm run admin:reset` выдаёт новый случайный пароль в тот же файл и завершает предыдущие сессии. Команда предназначена для локального владельца сервера.
- Настройки окружения перечислены в `.env.example`. По умолчанию сервер слушает только 127.0.0.1, а страницы закрыты от индексации.

## Что реализовано

17 страниц: 15 исходных и две новые — `/remont-v-novostroyke` и `/remont-vtorichnogo-zhilya`, в исходном шаблоне услуги. Старые смысловые URL сохранены. В каталоге 1045 текстовых полей: основной контент и FAQ разделены по страницам, контакты и меню остаются общими. Редактор показывает область действия правки. Оригинальные блоки и стили не заменены React-вёрсткой. React используется только в отдельной админке.

Подготовлена рабочая карта SEO: 88 формулировок в 16 группах, с ручным назначением основного URL. Частотность и пересечение выдачи не измерены. Карта и её ограничения — `_redesign/SEMANTIC_MAP.md`, данные — `_redesign/SEMANTIC_CORE.csv` и `.json`. Экспорт: `node scripts/export-semantics.mjs`. В существующие ответы добавлены 30 контекстных ссылок; их карта находится в `_redesign/INTERNAL_LINKS.json`. Раздел SEO админки показывает группу запросов для выбранной страницы.

SEO-миграция дополняет новые страницы и обновляет только неизменённые исходные тексты и метаданные. Пользовательские правки, цены и индивидуальный noindex сохраняются. Для миграции также нужны `scripts/seo-baseline-v2.json` и `scripts/editorial-baseline-v3.json`. Локальные страницы закрыты от индексации; внешний ссылочный профиль и продвижение по схеме «Удар шершня» не реализовывались.

После анализа конкурентов подготовлены отдельные вопросы и ответы для девяти услуг. Карточки главной связаны с косметическим, капитальным ремонтом и ремонтом по проекту. Цены взяты со страниц услуг исходного сайта по указанию владельца; расхождения с бывшими пакетами главной устранены. Обращение описано как обсуждение задачи, без обещания готовой сметы по одному телефону.

Раздел «Услуги и цены» хранит девять предложений: цену, единицу расчёта, состав, материалы, исключения, условия и вариант комплектации. Одинаковые цены и описания берутся из одной записи. Раздел «Портфолио» управляет шестью существующими объектами одновременно на главной и в галерее: название, площадь и её смысл, город, роль компании, сроки, тип материала. Недостающие в исходнике сведения не выдумываются; пустые дополнительные поля не выводятся. Исходные фотографии сохранены.

В заявке сохраняется услуга, в том числе определённая по странице обращения. Менеджер может заполнить сведения об объекте, площадь, состояние, наличие проекта, задачу, желаемое начало и следующий шаг. Первоначальное сообщение клиента при этом не изменяется.

Схема контента версии 2 автоматически переносит старые черновики и опубликованное содержимое при запуске. Пользовательские текстовые правки и SEO сохраняются, исходные записи истории остаются неизменными; при восстановлении старая версия преобразуется в текущую структуру. Перед обновлением работающего экземпляра выполните `npm run backup`. Файл `scripts/legacy-content-v1.json` нужен для отличия исходных текстов от редакторских правок; не удаляйте его при развёртывании.

Управление title/description/noindex каждой страницы; canonical формируется из домена и маршрута. Сервер сразу выдаёт опубликованные данные в исходном HTML, включая метатеги. Присутствуют H1, заголовки разделов, базовая структурированная разметка WebPage, Organization, BreadcrumbList и Service для девяти услуг. HTTPS sitemap, редиректы со старых `page*.html`, `/main`, нормализация завершающего слеша и настоящая 404.

Черновик → авторизованный предпросмотр → публикация → история. Восстановление помещает выбранную версию в черновик; отдельная публикация делает её публичной. Проверка ревизии предотвращает потерю параллельных правок.

Заявки сохраняются в SQLite до доставки уведомлений. Есть статусы, ответственный, заметки, журнал изменений, источник/UTM, версия содержания при обращении и защита от повторной отправки. Внешние каналы Telegram, Bitrix24, SMTP подключаются в админке; они отключены по умолчанию. Для ошибки одного канала предусмотрены независимые повторы, до пяти попыток. Отправку внешнему провайдеру невозможно гарантировать ровно один раз при сетевом таймауте после принятия сообщения; номер заявки помогает распознавать повтор.

Загрузка JPG/PNG/WebP с проверкой фактического формата, ограничением размера, автоматическим поворотом и оптимизацией. Замена фотографий и редактирование alt на существующих страницах. Логотип и декоративные PNG/SVG защищены от замены. Используемые в версиях фотографии нельзя удалить.

Роли `admin` и `manager`. Менеджер работает с заявками, фотографиями и черновиками; публикация, удаления, интеграции и управление пользователями проверяются сервером и требуют администратора. Пароли хешируются scrypt, сессии хранятся в БД, cookie — HttpOnly/SameSite Strict; есть CSRF, проверка Origin, ограничения запросов и журнал действий. Сессии отзываются при отключении пользователя.

Метрика включается в настройках и загружается после согласия посетителя. Цели: `lead_submit`, `form_start`, `phone_click`, `messenger_click`. Их нужно создать в кабинете Метрики. Реальные показатели посещаемости админка не имитирует.

## Сохранение оформления

Исходные файлы не изменяются. В шаблонах сохраняются классы, CSS, встроенные стили, порядок блоков и оригинальные изображения. Новые семантические теги имеют CSS-сброс стандартных браузерных отступов, не перекрывающий исходные классы.

В обычном состоянии формы сохраняют исходный набор видимых полей и уведомление об обработке данных. Согласие в API фиксируется как отправка формы с этим уведомлением; отдельный новый чекбокс не добавлялся, чтобы не менять согласованный дизайн. Итоговую формулировку и механику согласия следует утвердить вместе с политикой перед запуском. Сообщение об отправке появляется только при работе формы. Баннер аналитики появляется только после её включения.

Админка управляет существующими блоками и изображениями. Конструктор произвольных секций, добавление новых карточек/страниц проектов, видео, отдельный Telegram-бот для загрузки портфолио и подключение CRM-кабинетов не реализованы; эти возможности нельзя считать готовыми по факту наличия в чужом CASE.md.

## Сведения, которые должен подтвердить владелец

В админке есть раздел «Проверка сведений». Контакты, регион, цены, гарантии, принадлежность портфолио и отзывы перенесены как непроверенные исходные сведения. Их нельзя объявлять достоверными только из-за наличия на старом сайте.

Явные текстовые заглушки процесса заменены; исправлены формулировки диапазонов цен, безусловного изменения стоимости и недоказанных сроков ответа. Политика с данными потолочной компании заменена редактируемой заготовкой с noindex. Нужны действительные реквизиты и окончательный текст. В production API не принимает заявки, пока проверка политики не подтверждена. Сервер не даёт подтвердить её с пустыми реквизитами или оставленной заготовкой.

До публикации на действующем домене: заполнить реквизиты и контакты; исправить/подтвердить остальные пункты; проверить юридические тексты; подключить выбранные уведомления; проверить форму и доставку на согласованном обращении. Доступы к старому хостингу, DNS, Вебмастеру и Метрике в проект не предоставлялись.

## Проверки

```powershell
npm run build
npm test
npm audit
```

32 автоматических теста используют отдельные временные SQLite-базы. Они не создают заявки в рабочей базе и не отправляют сообщения во внешние каналы. Проверяются: HTML и метаданные всех страниц, неизменность исходных файлов и стилей, черновик/публикация/восстановление, XSS-экранирование, доступ и CSRF, роли, валидация и повтор заявки, ограничения запросов, независимая доставка с подменёнными каналами, медиа, редиректы/404 и восстановимость SQLite-снимка. Отдельный тест собранной админки проверяет вход, редактирование, сохранение, публикацию, предпросмотр и переходы между разделами через DOM.

В браузере проверены все 17 страниц при ширине 390 и 1440 пикселей, выбранные первые экраны, меню, FAQ, формы, карта и мобильный SEO-редактор. На отдельной базе проверены публикация и заявка. Результаты и ограничения — `_redesign/BROWSER_QA.json`; реальные внешние каналы и физические телефоны не проверялись.

## Хранение и резервные копии

Данные: `data/monolit.sqlite`, WAL и `data/uploads/`. Не заменять этот каталог при обновлении приложения. Не копировать только активный sqlite-файл обычной файловой копией.

```powershell
npm run backup
```

Скрипт создаёт согласованный SQLite-снимок через Backup API, проверяет целостность, копирует загруженные изображения и записывает манифест в `backups/<дата>/`. Незавершённая копия остаётся с суффиксом `.partial` и не считается готовой. Исходные шаблоны, CSS и изображения из экспорта хранить вместе с кодом отдельно. Бэкап содержит заявки, пользователей и секреты каналов; доступ к нему должен быть ограничен владельцем.

Для восстановления: остановить приложение, сохранить текущий каталог данных как страховочную копию, восстановить `monolit.sqlite` и `uploads` из выбранного бэкапа в **чистый** каталог DATA_DIR (не оставлять WAL/SHM от другой базы), проверить права и запустить приложение. Скрипт автоматического разрушительного восстановления намеренно не включён.

## Подготовка к VPS

Есть Dockerfile, `compose.yaml` и `deploy/Caddyfile`. Caddy выдаёт TLS, перенаправляет www и HTTP на основной HTTPS-домен и проксирует приложение. Backend не публикует порт наружу. `TRUST_PROXY=1` используется только за единственным доверенным Caddy; при прямом доступе к Node он должен быть выключен.

Создайте `.env` на VPS с `SITE_DOMAIN`, `INIT_ADMIN_LOGIN` и уникальным `INIT_ADMIN_PASSWORD` длиной от 12 символов. Не коммитьте секреты. Перед первым переключением домена сделайте резервную копию текущего сайта и проверьте новый на согласованном тестовом адресе.

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail 50 app
```

После приёмки перенести подтверждённую базу/изображения в volume, настроить DNS и проверить HTTPS, формы и редиректы. На обновлениях сохранять volumes. `docker compose down -v` удаляет данные и сертификаты — не использовать для обычного обновления.

Контейнерный запуск и действующий домен не считаются проверенными лишь по успешной локальной сборке. Публикация на brilliant-monolit.ru в ходе локальной разработки не выполнялась.
